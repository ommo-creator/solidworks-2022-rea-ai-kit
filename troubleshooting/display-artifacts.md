# 剖切/线稿显示异常：从"看着像显卡坏了"到根因

> 这一篇是一份**完整的诊断记录**：起因是一组看起来很吓人的症状——零件轮廓局部断裂、
> 白色块状遮挡、球面附近多重轮廓、显示不稳定、导出的图没法用来标注。
>
> 结论是：**都不是显卡、不是分辨率、也不是模型几何**。根因是显示样式 + 文档图像品质 +
> 导出路径三个独立因素叠加。下面是把它一步步钉死的过程，以及你可以直接复用的判据。

适用版本：SolidWorks 2022 SP5.0（30.5.0.0049）。方法本身与版本无关。

---

## 0. 症状清单（照抄用户描述）

| # | 现象 | 最终归属 |
|---|---|---|
| S1 | 零件轮廓局部断裂、碎线、缺线 | **显示样式**（着色面压掉边线）+ **图像品质过低** |
| S2 | 部分区域出现白色块状遮挡 | **显示样式**：剖开后的内腔面被拍成近白实心 |
| S3 | 球面/复杂叠装处多重轮廓，前后边线混杂 | **显示样式**：着色面的孔环 + 法兰边线 + 相切边线叠加 |
| S4 | 显示效果不稳定 | **导出路径**：`SaveBMP` 读前缓冲，窗口状态不同结果不同 |
| S5 | 导出的图不适合清晰标注 | **导出路径**：同上，且背景是主题渐变不是纯白 |

## 1. 先用像素数把"难看"变成"可测"

所有判断都建立在同一个量化口径上：**同一视角、同一区域、同一尺寸的导出图，
按亮度分带统计像素**。

```python
# 亮度分带：把"线"和"面"分开计数
import numpy as np
from PIL import Image

def bands(path):
    a = np.asarray(Image.open(path).convert("L"), dtype=np.int16)
    return {
        "dark_lt128":   int((a < 128).sum()),          # 真正的黑线
        "mid_128_190":  int(((a >= 128) & (a < 190)).sum()),   # 灰线/隐藏线
        "bg_190_235":   int(((a >= 190) & (a < 235)).sum()),   # 背景渐变 / 着色面
        "white_gt235":  int((a >= 235).sum()),         # 纯白
        "min": int(a.min()), "mean": round(float(a.mean()), 1),
    }
```

同一剖面、同一视角下扫全部五种显示模式，得到的是**一张判据表**，不是主观印象：

| 显示模式 | `<128` 深色线像素 | `128–190` 中灰 | 判读 |
|---|---|---|---|
| 线架图 (334) | 69,435 | 1,264 | 前后线全画，遮挡关系错 |
| **隐藏线消除 (335)** | **36,286** | **4,452** | **干净线稿，遮挡正确** |
| 隐藏线可见 (336) | 36,776 | 23,691 | 与 HLR 同量级，只是把隐藏线画成灰虚线 |
| 着色 (337) | 53,423 | 107,539 | 边线被面吃掉一部分，面变成大块灰 |
| 带边线上色 (506) | 77,646 | 97,359 | 边线最多但**互相叠加**，出现多重轮廓 |

**这张表直接否掉了两个常见误判**：

1. **不是"隐藏线消除失效"** —— HLR 与 HLV 的深色像素数几乎相同（36.3k vs 36.8k），
   差别全在中灰带（4.5k vs 23.7k）。HLR 一直在正常工作。
2. **不是"线太少/分辨率不够"** —— 带边线上色的线像素（77.6k）反而是 HLR 的两倍。
   问题不是线少，是**线互相叠着画**。

同时注意 `190–235` 那一带约 **94 万像素（≈25% 画面）**——那就是主题背景渐变。
纯白背景下这一带应该**全部是 255**。

## 2. 根因 A（主因）：显示样式是"带边线上色"

### 证据：同一区域三种模式的竖直对照

取顶盖法兰同一块区域，只在模式上做单变量切换：

| 模式 | 看到什么 | 对应用户症状 |
|---|---|---|
| **HLR（335）** | 黑色 1px 细线，螺栓孔是**完整闭合的小轮廓**，无着色、无灰块 | ——（这就是想要的效果） |
| **带边线上色（506）** | 零件呈**半透明感**（能看穿壁板），孔变成**浮在着色面上的小环**，与法兰边线、相切线叠成**三重轮廓** | S3 |
| **着色（337）** | **几乎没有边线**，孔只剩浅色环，壁板轮廓缺失；大面积灰/彩色面 | S1、S2 |

### 为什么带边线上色会"断线 + 白块"

- 着色面先画，边线后画，两者靠 **polygon offset** 分离（`Polygon Offset Factor/Units`）。
  当 offset 不够或深度精度不足时，边线被面**吃进**去 → 局部断裂/缺线。
- 剖切后露出的**内腔面**在着色模式下被光照拍成接近纯白，紧贴边线 → 看起来就是"白色块状遮挡"。
- 螺栓孔这类小圆柱，在着色模式下同时有"孔的真实边缘"+"面的边界"+"相切边线"三层，
  → 三重轮廓、前后边线混杂。

### 关键交叉验证：相切边线其实无关

用命令号 1515（移除相切边线）前后对比 → **差异 0 像素**；恢复后差 5 像素（噪声级）。

> 这条很重要：直觉会说"多重轮廓一定是相切边线造成的"，实测**不是**。
> 单变量测试在这里省掉了一整条错误路线。

## 3. 根因 B（次要但真实）：文档图像品质只有 61

`IModelDoc2.GetTessellationQuality()` 是**按文档存**的，和用户全局设置
（System Options → Image Quality → Tessellation Number）是**两层不同参数**。

本例中：全局设置 = 80，**文档实际 = 61**。

```
61 → 100 后重新 `EditRebuild3`：与基线差 8,066 像素（约占线像素 23%）
100 → 61 复原则回到基线（差 5 像素）
```

放大 3 倍看：品质 61 时圆柱端面、六角、小孔**全是折线拼接**；100 时才是光滑曲线。
→ **这是"碎线"的一个独立贡献项**，但它不会造成断线，也不会造成白块。

```python
q = md.GetTessellationQuality()        # -> 61
md.SetTessellationQuality(100)
md.EditRebuild3()                      # 必须重建才生效
```

> 注意：`SetTessellationQuality` 改的是**文档**属性，会改变文档状态。
> 对只读交付文档要先备份，或改完立刻改回去并**不保存**。

## 4. 根因 C（容易被忽略）：`SaveBMP` 读的是前缓冲，不是离屏渲染

这是"导出的图不适合标注"的直接原因，也是最反直觉的一条。

### 决定性对照

| 状态 | 导出图统计 |
|---|---|
| SolidWorks 窗口**最小化**时 `SaveBMP` | `min=221.7`，`mean=244`，**`<128` 像素 = 0**，`<220` 像素 = 0 |
| 把窗口**恢复并前置**后立刻 `SaveBMP` | `min=0`，**`<128` = 35,273**，暗像素包围盒 (1055,254)–(1848,1088) |

更狠的证据：**四种完全不同的剖面设置**（封盖开/关 × 图形剖切/真剖切）导出的四张图，
亮度统计**完全一致**（`<250`:2041049、`<240`:1280519、`<220`:0、`<128`:0）。
四种不同状态出同一张图 = 前缓冲从未重绘。

### 结论

- `SaveBMP` **返回 `True`**，但存下来的可能是上一帧、甚至是空白帧。
- 它依赖"窗口可见 → 系统重绘 → 前缓冲是新的"这条链路。
- `md.GraphicsRedraw2()` 在本版本返回 `False`，**不能**当作"已重绘"的判据。
- 唯一真正强制重绘的操作是**改变模型状态**（例如建立真剖切、重建），
  这也是为什么"只有真剖切那张图里有黑线"。

### 所以导出必须自带校验

```python
def export_ok(md, path, w=2560, h=1440):
    assert md.SaveBMP(path, w, h)
    a = np.asarray(Image.open(path).convert("L"))
    n_dark = int((a < 128).sum())
    if n_dark < 200:                   # 经验阈值：正常线稿至少几千个暗像素
        raise RuntimeError(f"导出疑似空/陈旧帧：dark={n_dark}")
    return n_dark
```

### 正确的导出姿势

1. 确保窗口**可见**（restore + 前置），不要最小化。
2. 先做一次**会改变模型状态**的操作（切显示模式、重建、建剖面）逼出重绘。
3. `SaveBMP`。
4. **统计像素**确认不是空图。
5. 需要更高保真时，改用 `IModelView.GetViewDIBx64()` 直接取位图，或用
   `Extension.SaveAs` 出 PDF/图片（走不同的渲染路径）。

## 5. 你提的"纯白背景"其实只差一个下拉

排查时发现一件有意思的事：三个"背景色"注册表值都已经是**纯白 16777215**：

```
Top Gradient Color      = 16777215
Bottom Gradient Color   = 16777215
Viewport Background     = 16777215
```

但它们**没有生效**，因为被另一组值覆盖：

```
Background Appearance   = 3            ← 3 = 渐变/图像，此时用的是 Background Image
Background Image        = smoke.png    ← 主题自带的渐变图
Active Color Scheme Name = Smoke
```

**改法（界面，30 秒）**：System Options → Colors → **Background** 选"单色 (Plain)"，
然后把颜色设为白。切到"单色"后，上面那三个纯白值才生效。

> 注意：`Background Appearance` 这一档**没有**可用的 Python 通道。
> `comtypes.gen.SldWorks` 里一个 `sw*` 常量都没有（见 `data/enums.json` 的说明），
> 而 `swUserPreferenceIntegerValue_e` 的取值只能靠 `SetUserPreferenceIntegerValue(枚举号, 值)`，
> 硬编码枚举号在跨版本时非常脆弱。**这类一次性设置用界面改更划算。**

## 6. 排除掉的嫌疑（附证据，省你再查一遍）

| 嫌疑 | 测试方法 | 结果 |
|---|---|---|
| 装配体未完整加载 / 轻化组件 | `GetComponents` 计数、`IsSuppressed`/`IsHidden` | 400 个组件，压缩 0、隐藏 0，`OpenDoc7` 报 `Error=0 Warning=0` |
| 重建错误 | `EditRebuild3()` | 返回 `True` |
| 注解 / 草图 / 基准面在画面上捣乱 | 逐项开关 8 个显示项 + "隐藏所有类型" | 注解数 = **0**；各开关两次切换后与基线差 **0 像素** |
| 相切边线造成多重轮廓 | 命令 1515 / 1545 对照 | 差 **0 像素** |
| 剖面封盖造成白块 | 封盖开/关对照（HLR 下 **251 px**，着色下 **129 px**） | 封盖几乎不影响画面 |
| 草稿品质 HLR | 命令 298 对照 | 当前**本来就是关的**；开启反而少约 20k 线像素（更粗） |
| 显卡驱动崩溃 | 系统日志 `Display` / `nvlddmkm` | 近 7 天无 SLDWORKS 崩溃；仅 1 次驱动恢复且与本次症状无关 |
| 远程桌面 / 虚拟显示 | `SESSIONNAME`、`qwinsta`、显示适配器枚举 | Console 会话、单屏直连（虚拟适配器存在但非活动） |
| 硬件 vs 软件 OpenGL | 进程窗口类名 | 存在 `NVOpenGLPbuffer` 类窗口 → 走的是**硬件 OpenGL ICD**，不是 Mesa 软件光栅器 |

### 一条仍然成立的"较可能"

**SolidWorks 2022 不识别比它新的显卡。** 证据是两条：

1. `HKCU\Software\SolidWorks\Diagnostics` 的 `GFX Card Model` 为**空字符串**
   （正常情况下会写入型号）；`GFX Card Driver Version = R615`、`Last Validated SW Version = 2022`。
2. 安装目录里 SW 自带的显卡 workaround 库 `lang\graphicshardware.reg`（3,539 行）
   **完全没有 GeForce 条目、也没有 RTX 40/50 系列**，NVIDIA 部分只覆盖到
   `Quadro RTX *` / `RTX Axxxx` / `T*` / `Tesla` / `TITAN`。

→ 这类新卡会走**通用渲染路径**，没有针对性的 polygon-offset/深度精度 workaround。
这与"边线被面吃掉"高度一致，但**我们没有做 A/B**（换卡/软件 OpenGL 需要关文档重启，
超出可恢复测试的边界），所以只能标"较可能"，不能声称已证实。

> 对应地：**不要**看到断线就断言"显卡/驱动坏了"。本例中驱动侧没有任何崩溃记录，
> 而同一张显卡在 HLR 模式下完全正常。

## 7. 最小必要修复（按收益排序）

| 步骤 | 操作 | 关文档/重启 | 收益 |
|---|---|---|---|
| 1 | 视图切到 **隐藏线消除**（`RunCommand(335)`） | 否 | **主因消失**：断线、白块、多重轮廓一起没了 |
| 2 | **图像品质** 61 → 100（`SetTessellationQuality(100)` + 重建） | 否 | 曲线/圆孔不再折线化 |
| 3 | 背景改"单色"并设为白 | 否 | 纯白背景 |
| 4 | 关闭"在着色模式下显示阴影" | 否 | 去掉地面投影阴影 |
| 5 | 导出前恢复窗口 → 导出 → 统计像素校验 | 否 | 消除空图/陈旧帧 |
| 6 | 需要时再评估图形加速相关项（增强图形性能 / 软件 OpenGL） | **是** | 未验证，收益未知 |

前 5 步都是**视图级**操作，不改几何、不改配合，且可以随时切回。

### 修复前后的量化对照（同一视角、同一剖面）

| 指标 | 修复前（带边线上色） | 修复后（HLR） |
|---|---|---|
| `<128` 深色线像素 | 77,646 | **36,286** |
| `128–190` 中灰像素 | 97,359 | **4,452** |
| 螺栓孔轮廓 | 浮在着色面上的环 + 三重轮廓 | 单层闭合细线 |
| 背景 | 主题渐变（`190–235` 带 94 万像素） | 可做到纯白 |
| 封盖填充斜线 | 无（HLR 不填充封盖） | 无 |

## 8. 可复用的诊断顺序（下次照着走）

1. **量化症状**：导出同视角图，按亮度分带统计。先把"难看"变成数字。
2. **单变量扫显示模式**：五种模式各导一张，看 `<128` 与 `128–190` 两列怎么变。
   —— 这一步通常就能定位到主因，而且**不需要改任何设置**。
3. **验证导出链路本身**：把窗口最小化再导出一次，看暗像素是否为 0。
   如果最小化和可见时结果不同，问题在导出，不在模型。
4. **查文档级参数**：`GetTessellationQuality()`，与用户全局设置比对。
5. **逐项开关显示项**（每次只改一项，改两次回到原位，验证 `B|base == 0`）：
   注解 / 草图 / 基准面 / 轴 / 临时轴 / 原点 / 相切边线 / 草稿品质 / 隐藏所有类型。
6. **只有在异常"固定在同一个坐标"时**，才去查模型：无效几何、重复组件、重合面、干涉。
7. **最后**才碰渲染路径（增强图形性能 / 软件 OpenGL），而且要知道它会强制关文档重启。

> 这套顺序的价值在于：**第 2、3 步就能否掉 80% 的常见误判**，
> 而且全程不改任何持久设置。

## 9. 关于那些"去不掉的线"

排查中画面上始终有一条第 1 条**贯穿全模型的竖直点划线**，以及几处孤立的**小箭头状轮廓**。
穷举测试结论：

- 注解总数 = **0**（`GetAnnotations` 无对象）
- 命令 404 / 3120 / 3119（各级注解开关）→ 与基线差 **0 像素**
- 命令 339 / 99 / 126 / 338 / 403 / 511 / 402（轴/临时轴/原点/平面/草图/点/曲线）→ 逐项复原后差 **0 像素**
- 命令 1810（隐藏所有类型）→ 差 1,667 像素（与草图开关同量级，属噪声）

→ 判为**零部件内部的装饰性几何**（模型自己的线，不是视图生成的）。
这类东西只能靠"在模型里点选确认后删除/隐藏"，**显示设置永远去不掉**。

---

## 10. 一句话总结

> 断线、白块、多重轮廓的根因是**用着色模式看剖切**——面压边线、内腔面拍白、孔环叠边线；
> 碎线再叠加**文档图像品质 61**；导出不好用是**`SaveBMP` 读前缓冲**。
> 换成隐藏线消除 + 拉满图像品质 + 导出后校验像素，三个症状同时消失，
> 而显卡、驱动、分辨率、模型几何都是清白的。
